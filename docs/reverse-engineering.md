# Comparing Vertigo with the original

How to settle the open questions in [ROADMAP.md](ROADMAP.md#open-questions-and-how-to-settle-them)
by observing the original game, without copying its code. Written October
2026 after a survey of the repository, of
[sfwin32](https://github.com/mnkraus/sfwin32) at commit
`e0861140e62f0934432ad05b0d0813ab48b5d670` (read only, in a scratch directory)
and of the GOG installation on this Mac (checksums match the roadmap's table).

## What we have

- The GOG installation (German, software and 3dfx builds, `game.gog`, the AD
  Augmented Mod 1.2 next to it). It ships its own DOSBox, including a
  `dosbox_debug.exe` (DOSBox SVN 2011 with the heavy debugger), Windows only.
- `FIGHT.EXE` runs a mission on its own. `SF.EXE` only chains the two halves:
  `DESKTOP.EXE` writes `DAT\SAVE\FIGHTIN.DES` and exits with code 2, then
  `FIGHT.EXE` is started with the single argument `solo` and reads that file,
  whatever the command line (sfwin32 traced both; the file names are in the
  executable's strings). `FIGHTIN.DES` is plain text: map, mission, scenario,
  boat and its mountings, difficulty, display and sound settings; the four
  `FTRAI*.DES` are ready-made examples. So any scenario can be started in the
  original exactly as `vertigo s00406 --boat 2050 --equip …` does, with the
  same loadout, and `FIGHTOUT.DES` tells how it ended.
- The Miles Sound System in both executables has its call logging compiled in
  (strings `MSS_DEBUG`, `MSS_SYS_DEBUG` and the log header "Miles Sound
  System usage script generated by MSS V3.50F"; Miles 3.x documented this as
  an environment variable naming the log file, `AIL_DEBUG` in 3.01). A log of
  every `AIL_set_sample_volume`, `_pan`, `_playback_rate` and `_start_sample`
  call with timestamps, straight from the original, needs only `SET
  MSS_DEBUG=C:\MSS.LOG` before the start. Confirmed (October 2026): the log
  appears at once with the init calls, then every `AIL_init_sample`,
  `_set_sample_address`, `_set_sample_playback_rate`, `_set_sample_volume`,
  `_set_sample_pan`, `_start_sample` and `_end_sample` with millisecond
  timestamps and the sample's handle; 20 KB after 20 s of a mission.
- This Mac is Apple silicon with no emulator, VM or disassembler installed.
  Homebrew offers native builds of everything needed: `dosbox-x` (built with
  `--enable-debug=heavy`, i.e. the full debugger), `ghidra`, `rizin`,
  `radare2`, and the `utm` cask for a Windows VM.
- Vertigo's test mode already produces what a comparison needs on its side:
  `--trace` (cell, height, speed, shield, order, current, head motion per
  second), `--fixed-step`, `--screenshot`, `--keys`, `--seed`, exit codes and
  `FIGHTOUT`-like summaries.

## Three instruments, in the order to reach for them

### 1. The original in DOSBox-X on this Mac (behaviour, memory, sound log)

Native, free, and the only one that needs no Windows. It answers every
"watch the original" question in the roadmap's table.

- Install: `brew install dosbox-x`. Mount a *copy* of the game folder (never
  the GOG installation itself; the game writes saves, `FIGHTOUT.DES` and
  possibly logs) and the CD image for the music (`imgmount d game.ins -t iso`
  as GOG's config does). Start it from a terminal, which the debugger needs.
- Launch a mission directly: write `DAT\SAVE\FIGHTIN.DES` (copy an `FTRAI`
  file, change `Map`, `Mission`, `Dramaturgy` and the ship) and run
  `FIGHT.EXE solo` from the `[autoexec]` section. No menu driving, no story
  state. This is the counterpart of `vertigo s00406`.
- Observe:
  - Screen: Ctrl+F5 screenshots, Ctrl+Alt+F5 video, or `DX-CAPTURE FIGHT.EXE
    solo`, which records the whole run to AVI and WAV. Compare with
    `--screenshot` and `--fixed-step` runs of Vertigo in the same scenario
    with the same loadout (D12, D13, radiation, cluster burst, dust, debris,
    the building with `card` in s00401).
  - Memory: the heavy debugger (Alt+F12 breaks in; `DEBUGBOX FIGHT.EXE solo`
    breaks at the entry) has `BPLM <linear>` (break when a dword changes),
    `BPINT 21 3D` (break on file opens), `MEMDUMPBIN <seg>:<off> <len>` and
    instruction logs. The executable's link-time layout is known from
    sfwin32's analysis (two objects, code at `0x10000`, data at `0x140000`,
    all 20,165 fixups internal); the extender (CauseWay 3.25 in `FIGHT.EXE`,
    which its crash screen names; `DOS4GW.EXE` is for the other executables)
    loads them at another base, which one `BPINT 21 3D` on the open of
    `fightin.des` reveals (EDX holds the file name, whose link-time address
    is known). From there a `MEMDUMPBIN` of the player's or a unit's record
    every few seconds is the original's `--trace`. Without any address, a
    differential dump works too (done for the currents, see below): dump the
    game's whole data range every second or two, then look for the fields
    that change consistently with the motion.
  - Scripted runs: `[dosbox] mcp_server=<port>` makes DOSBox-X connect to a
    local TCP server and take debugger commands (`REQ <id> EXEC <command>`),
    so a small Python script can run a scenario, dump memory on a schedule and
    stop, repeatably; `ADDKEY` injects keystrokes. Fixed `cycles` (not `max`)
    keep runs comparable.
  - Sound: `SET MSS_DEBUG=…` (above) before `FIGHT.EXE`, then relate the
    logged volume and pan values to the distances in a memory trace. This
    settles the engine-sound falloff (roadmap: "how engine volume and pan fall
    off with distance") without sfwin32.
  - Outcome: `DAT\SAVE\FIGHTOUT.DES` after the run (completed, failed,
    primary, secondary, destination), the same as Vertigo's exit code and
    summary line. Good for G5 (Schwartz in s00705), "Explode counts as
    destroyed" (s01804) and the unresolved conditions.
- The 3dfx build (`FIGHT3.EXE`) needs a Glide wrapper, which DOSBox-X only has
  on Windows. Nothing in the open questions depends on it; the software build
  is the one to compare with.

[CLAUDE.md](../CLAUDE.md) allows this since October 2026: the DOS executables
may run on the host under DOSBox-X only, with a copy of the game folder as the
only mount. The VM rule was written for sfwin32, which runs the game's x86
machine code natively in a Windows process and patches it; a DOS program under
DOSBox-X runs in a CPU interpreter and can reach nothing but the mounted
directories. The risk left is DOSBox-X's own bugs, the risk of any emulator.
sfwin32 and its `fightport.exe` keep the VM rule.

### 2. Reading `FIGHT.EXE` statically on this Mac (meanings of keys and tables)

For the questions no amount of watching settles cheaply: what `sle` means,
what `car` does for towers and ambush, `con` for Explode, `diff`, the mission
end types, `wccond 9`, whether a slot with a break condition also ends by
itself, the exact current speeds and the radiation trigger.

- Tools: Ghidra (`brew install ghidra`) with an LE loader extension
  ([ghidra-lx-loader](https://github.com/oshogbo/ghidra-lx-loader) or
  another LX/LE loader), or, if the loader balks at DOS/4GW's stub, a small
  script of our own that applies the LE fixups and writes the two objects flat
  (the format is public and the job is a hundred lines; sfwin32's
  `le_extract.py` does the same, but it stays in its scratch directory), loaded
  as raw memory blocks at `0x10000` and `0x140000`. rizin and radare2 read LE
  natively and are enough for quick looks.
- Calling convention: Watcom register calls, arguments in EAX, EDX, EBX, ECX,
  callee cleans the stack (sfwin32's `PLAN.md` measured this). Ghidra needs a
  custom prototype model for it; without one its decompiler output is
  misleading.
- Method: the scenario loader is table driven. The key strings are in the
  binary (`sle`, `inte`, `eint`, `card`, `car`, `con`, `diff`, `spd`, `num`,
  `dis`, `hei`, `wccond`, …, found by `strings`). Each string's reference leads
  to the parser entry that stores the value at an offset of the unit record;
  every read of that offset in the rest of the code is where the key matters.
  That is one function per question, read as a viewer, and it yields a
  behavioural statement ("`sle` 1 makes the unit start asleep until …") plus
  constants. Combined with instrument 1 (set a `BPLM` on that field, or
  change the key in a copy of the scenario and watch), a reading is confirmed
  in minutes.
- What goes into this repository: behaviour, formulas in words, constants and
  units, and the scenario or test that confirmed them, in the roadmap's
  appendix. Not addresses, not disassembly, not decompiler output, not names
  of the original's functions. Keep the analysis notes in the scratch
  directory or a private notebook. For a GPL code base that is the line
  between observing and copying, and it is also what keeps the two engines
  from converging on the original's bugs by accident.
- Clean room, with two sessions: an analyst session reads the binary and
  writes the behavioural notes; an implementer session, which never sees
  disassembly, codes from the notes and from Vertigo's own data analysis. The
  notes are the contract, and a disagreement between the two is a test case.

### 3. sfwin32 in a Windows VM (instrumented execution)

sfwin32 is a static port: the original code runs natively, with DOS, VESA,
the timer and Miles replaced, and with `--watch ADDR[:N]` (log a global or a
struct when it changes), `--calltrace` (every Miles call with its caller),
`--patch ADDR=BYTES` (change behaviour at a byte) and a verification mode that
runs an original function and a C replacement side by side. It also carries
the project's recovered knowledge: the Miles entry points of all three
builds, the ISR and stack-probe sites, the handoff protocol.

- It needs 32-bit Windows x86. On this Mac that means Windows 11 ARM in UTM
  (Homebrew cask `utm`), whose built-in x86 emulation runs 32-bit
  applications; whether a vectored-exception-handler port like this survives
  that emulation is untested (the roadmap says so too), and the checklist in
  the roadmap applies in full: offline VM, snapshot, non-admin user.
- Use it when instruments 1 and 2 are not enough: a global that must be
  watched at every write with its caller, a behaviour to switch off by a byte
  patch to see what changes, or a function to A/B against a C rewrite. For
  the current list of open questions none requires it; the Miles log and the
  DOSBox-X debugger cover `--calltrace` and `--watch`.
- Also a reference to read: `audio.c` (how Miles' volume, pan and rate calls
  are meant), `services.c` (what the game asks of DOS), `PLAN.md` (the
  binary's layout and conventions). Reading it is allowed; its findings about
  the game's structure can be used, its code and the game's cannot.

## A differential harness

The payoff is in comparing like with like, repeatedly:

1. One scenario, one loadout, one `FIGHTIN.DES` and the equivalent Vertigo
   command line (a script can generate both from the scenario id, boat and
   equipment).
2. Same inputs: the idle player (engine off, no keys) first, then a few keys
   at fixed mission seconds (`--keys` on our side, `ADDKEY` or the control
   channel on theirs).
3. Same observations, as a function of mission time rather than frames (the
   original's clock runs at 200 Hz on the PIT, Vertigo's physics at 20 ms
   steps): position and height of the player and of a few units every
   second, shields, the current order slot, the sound calls, the outcome.
   Vertigo's `--trace` is the format; the original's side is a memory dump
   decoded by a script.
4. Diff. Where the curves part, look at that moment in the recording and, if
   it is a rule and not a constant, in the code (instrument 2).

Start with the questions whose answer is a number, where this pays at once:
current speeds (s00406, s01806, engine off, drift per second), the engine
sound falloff (one unit, the player approaching), the mine column spacing
(s00201 screenshots), the hit effect sizes (D13).

## The DOSBox-X workflow as set up (October 2026)

Everything lives in `~/Documents/Legacy/AD-dosbox`, outside the repository:
`game/` is the GOG folder without `game.gog`, `DOSBOX`, the installer and
the mod; `ad.conf` mounts it as `C:`, mounts the CD image read-only from
its original place, sets `MSS_DEBUG`, queues the keys with `AUTOTYPE` and
runs `FIGHT.EXE solo`; `setup_run.py SCENARIO AREA PX PY [HEI [CARD]]`
restores a scenario copy from its `.orig`, moves the player's start and
writes `DAT\SAVE\FIGHTIN.DES`; `cellmap.py` prints a scenario's current
cells with the player and the armed units; `dbxctl.py` is the control
channel's other end. Start it first, then `cd` to the work directory and
start `dosbox-x -conf ad.conf` from a terminal. What was learned:

- `memory io optimization 1=false` in `[dosbox]`, or the briefing's text is
  doubled and the lower half of the screen is noise. Don't resize the window
  while the game runs, that garbles it too.
- `AUTOTYPE -w 25 -p 2 space` in the autoexec presses the key that ends the
  briefing about 25 s after boot (the mission starts about 7 s later);
  `c` stops the boat and the key `grave` (left of 1) is the engine. The boat
  starts a mission at rest, so neither is needed for a drift measurement.
  The Terminal panel's keystrokes don't reach the game, and macOS refuses
  `osascript` keystrokes without the accessibility permission.
- The control channel: `mcp_server=58991` in `[dosbox]`; DOSBox-X connects
  to a listening script and takes `REQ <id> BREAK`, `REQ <id> EXEC <debugger
  command>` and `RUN` (README.debugger in DOSBox-X's source). While a
  command runs the emulation is stopped, and a 12 MB `MEMDUMPBIN` takes
  about a second, so the game's own clock (a 200 Hz counter, or the
  mission-time floats in every unit record) is the time base, not the wall
  clock. Two traps: the file name of `MEMDUMPBIN` goes through the
  debugger's expression parser, which uppercases it and takes `/`, `-` and
  `.` as operators (one run filled the repository with a 4 GB `BIN`), so
  dump to a plain name in DOSBox-X's working directory and move the file;
  and selector 0 wraps offsets to 16 bits, so address the dumps through the
  game's flat `DS` (`MEMDUMPBIN DS:400000 B7C000 MEMDUMP` covers the
  11.5 MB the game has mapped; `PAGING` lists the ranges).
- The game crashes (CauseWay exception 0E) if a scenario copy is stripped
  of its units, so measure in scenarios whose current cells are far from
  armed units (`cellmap.py`), not in doctored ones. With the player moved
  into a current the mission runs as usual; with it moved into s00406's
  base it is shot within 20 s.
- The drift measurement: dumps every 1–2 s with the boat at rest in a cell,
  the position found by diffing dumps (three floats, map cells × 512), the
  speed as the position's derivative over the game clock, cross-checked
  with the HUD's km/h readout in screenshots taken alongside
  (`screencapture` every 2 s, the readout cropped). Results in the roadmap,
  appendix D.
